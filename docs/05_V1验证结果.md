# 05 V1 验证结果

> **历史实验（已废弃、非当前生产方案）**
>
> 本文封存早期固定实验环境的 V1 结果，其中 VNC/noVNC、XFCE 和旧 Compose 只
> 代表当时调试背景，不得作为 CFserver 生产 runbook。当前生产事实以
> [验证总览](validation.md) 及对应日期的生产验证记录为准。

## 记录范围

当时实验覆盖 agent-wechat 的部署、登录、消息、部分文件、群聊、引用和合并转发
外层识别。`Verified` 只表示该轮固定实验环境实际通过，不能外推为当前生产复验。

历史实验环境使用 Debian 13、Docker、XFCE 和 noVNC/VNC。该桌面路径已经废弃，
当前生产固定 `ENABLE_VNC=0` 并使用容器内 `DISPLAY=:99`。

## 当时 API 结果

| 方法 | 路径 | 历史验证行为 |
| --- | --- | --- |
| GET | `/api/status/auth` | 返回登录状态 |
| GET | `/api/contacts` | 读取联系人 |
| GET | `/api/chats` | 读取聊天 |
| GET | `/api/messages/{chat_id}` | 读取指定聊天消息 |
| POST | `/api/messages/send` | 使用 `chatId` 与 `text` 发送文本 |

该轮历史实验还记录了 `GET /api/status/auth` 的下列关键字段：

```json
{
  "status": "logged_in",
  "loggedInUser": "<BOT_WECHAT_ACCOUNT_ID>"
}
```

这只证明当时响应中存在这些字段，不表示完整响应 schema 或跨版本契约已经冻结。

响应 schema、分页、错误码、时间语义和跨版本兼容性没有由该轮实验冻结。公共记录中
的账号、聊天和消息标识必须使用占位符。

## 历史文本发送与消息字段

该轮实验曾通过 `POST /api/messages/send` 按 `chatId` 发送文本。当时验证使用的
请求体为：

```json
{
  "chatId": "<CHAT_ID>",
  "text": "<REDACTED_MESSAGE_CONTENT>"
}
```

当时的成功响应包含 `success=true`。该轮发送接口使用的是 `text` 字段；
`content` 当时不是该接口的发送字段，但它曾作为读取消息时的内容字段出现。

该轮通过 `GET /api/messages/{chat_id}` 曾观察到以下消息字段：

- `sender`
- `senderName`
- `content`
- `timestamp`
- `isSelf`

这些证据只确认字段在当时固定环境中存在；分页、排序、时间单位、字段可选性和
完整错误契约没有由该轮实验冻结。

## 历史文件与 media 验证

当时从微信向已验证聊天发送 `txt` 和 `zip` 文件后，消息 API 曾识别到：

- 文件消息的 `type=49`；
- 消息包含 `localId`；
- 文件名可从 `filename` 或对应的 `content` 信息取得。

该轮使用的 media 接口为：

```text
GET /api/messages/{chat_id}/media/{local_id}
```

当时验证到的关键响应结构为：

```json
{
  "type": "file",
  "data": "<BASE64_DATA>",
  "format": "<FILE_FORMAT>",
  "filename": "<FILE_NAME>"
}
```

`txt` 和 `zip` 文件当时均成功取得 Base64 数据。该结论只覆盖微信侧接收、消息
识别和 media 获取，不表示 `POST /api/messages/send` 曾支持文件发送，也不表示
文件内容解析、所有文件格式或上层附件处理已经完成。

## 历史群聊与引用验证

该轮群聊实验曾验证：

- 使用群 `chatId` 定位聊天；
- 读取群消息并识别发送者；
- 识别群文件消息；
- 群消息返回 `isGroup=true`。

当时文本消息引用和文件消息引用曾返回 `reply` 上下文，关键结构为：

```json
{
  "reply": {
    "sender": "<EMPLOYEE_WECHAT_SENDER_ID>",
    "content": "<REDACTED_MESSAGE_CONTENT>"
  }
}
```

这说明当时调用方可以取得被引用消息的发送者和内容。引用消息 ID、引用层级、
已删除消息及更多富媒体引用结构没有由该轮实验验证。

## 历史合并转发边界

该轮曾在群聊中发送微信“合并转发聊天记录”，并通过
`GET /api/messages/{chat_id}` 读取外层消息。当时外层结构包含：

```json
{
  "type": 49,
  "content": "<MERGED_FORWARD_TITLE>"
}
```

当时还曾观察到 `localId`、`serverId`、`sender`、`senderName`、`timestamp` 和
`isSelf`。由于普通文件消息和合并转发外层都可能是 `type=49`，该轮不能只依赖
类型值判断消息语义。

使用 `GET /api/messages/{chat_id}/media/{local_id}` 尝试取得合并转发内部内容时，
当时返回：

```json
{
  "type": "unsupported",
  "format": "",
  "filename": ""
}
```

因此该轮历史边界是：

- 外层存在性、发送者和标题识别：已验证；
- 内部聊天记录、内部文本和内部文件展开：未支持。

该 `unsupported` 响应是当时 V1 media API 的明确能力边界，不影响外层识别结论，
也不能外推为后续版本的当前行为。

## WebSocket 消息事件

`/api/ws/events` 当时可以建立连接，但没有观察到微信新消息事件。在该轮记录中，
该能力保持 `Pending Investigation`，不能据此宣称实时消息事件已经可用。

## 历史 V1 Staging 旁证

早期 V1 Staging 曾验证外围调用方通过 agent-wechat 读取并回复微信文本。当时关联
Gateway 仓库记录的检查结果为：

- `pytest: 393 passed`
- `ruff: passed`
- `git diff --check: passed`

这些结果只是跨项目 Staging 文本联调的历史旁证，不是本仓当前测试结果，也不是
2026-08-13 CFserver 生产复验结果。它们不证明媒体、文件、Skills 或生产可靠性
已经完成。

该轮还记录了群聊线程上下文偏差：目标隔离键应为 `bot + group + sender`，但关联
Gateway V1 当时仍按 whole-room 聚合。这是外围调用方的历史已知偏差，不是
`CF_agent-wechat` 的内部实现或当前生产结论。外围系统的身份、权限、线程、AI 调度、
消息存储和防回环实现仍不属于本项目文档范围。

## 历史限制

- VNC/noVNC 和额外修复服务只属于历史实验，已废弃、非当前生产方案。
- 微信客户端登录与容器健康是不同状态源。
- 部分文件入口识别不等于系统文件处理或压缩包内容解析。
- 图片发送、API 文件发送和实时消息事件未验证。
- 历史跨项目文本联调不表示媒体、文件、Skills 或生产可靠性已经完成。
- `pytest: 393 passed` 属于当时关联 Gateway 仓库，不能记作本仓当前测试结果。
- whole-room 群聊线程聚合属于当时外围调用方的已知偏差。

当前接口边界见 [API 文档](api.md)，当前三态矩阵见 [验证总览](validation.md)。
