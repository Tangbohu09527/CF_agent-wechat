# 架构设计

## 生产拓扑

```text
Debian host
├── /opt/cf-agent-wechat
│   ├── scripts/bootstrap-cfserver.sh
│   ├── scripts/status.sh
│   ├── scripts/login.sh
│   └── docker/compose.cfserver.yaml
├── /srv/storage/cf-agent-wechat
│   ├── data
│   ├── wechat-home
│   └── secrets/auth-token
└── Docker
    ├── cf-agent-wechat
    │   ├── /data
    │   ├── /home/wechat
    │   ├── WeChat Linux
    │   └── agent-server :6174
    └── external network: cf-internal
            └── Gateway / other approved callers
```

生产 Compose 只定义本项目的 `agent-wechat` 服务。Gateway 是外部调用方，不在本仓
Compose 生命周期内。

## 容器与网络

- 容器名默认 `cf-agent-wechat`；
- restart policy 为 `unless-stopped`；
- 容器内 agent-server 监听 `0.0.0.0:6174`；
- 宿主默认发布到 `127.0.0.1:6174`；
- 容器调用方在 `cf-internal` 中通过 `cf-agent-wechat:6174` 访问；
- healthcheck 请求容器内 `http://127.0.0.1:6174/health`；
- 生产模式保留内部 Xvfb 桌面但关闭 VNC/noVNC。

服务没有 TLS。loopback 发布用于宿主运维检查，不是远程公共入口。

## 持久化映射

| 宿主路径（相对 `CF_RUNTIME_ROOT`） | 容器路径 | 作用 |
| --- | --- | --- |
| `data` | `/data` | 数据库、服务元数据和运行状态 |
| `wechat-home` | `/home/wechat` | 微信配置、缓存和会话 |
| `secrets/auth-token` | `/data/auth-token` | 只读 API Token |

默认 `CF_RUNTIME_ROOT=/srv/storage/cf-agent-wechat`。Compose 的兼容变量
`CF_AGENT_WECHAT_RUNTIME_ROOT` 必须解析到同一路径。

bind mount 设置 `create_host_path: false`，避免路径拼错时由 Docker 悄悄创建空目录。
bootstrap 先建立并校验目录，再启动 Compose，并在启动后检查容器实际 mount source。

## 启动路径

```text
bootstrap
  -> 检查 Docker Engine / Compose v2
  -> 校验或创建 env、runtime、Token
  -> 校验 Compose，创建 cf-internal
  -> compose up -d agent-wechat
  -> container running + Docker health healthy
  -> 校验 restart policy 和三个 mount
  -> /health 可用
  -> auth API 可读
```

bootstrap 可以由 root 或具 sudo 权限的普通用户运行。推荐普通用户直接执行，让脚本只在
创建受保护目录或访问 Docker 时按需 sudo。裸 `sudo ./scripts/bootstrap-cfserver.sh` 可能
丢失调用 shell 中的路径和镜像变量，不是推荐入口。

重跑 bootstrap 复用现有 env、Token 和持久目录。发现已有数据但 Token 缺失、目录类型或
权限错误时 fail-fast，不生成替代 Token，也不清理现场。

## 重启与会话恢复

```text
container/daemon/host restart
  -> unless-stopped 恢复容器
  -> 同一 bind mount 重新挂载
  -> status.sh --wait 检查四层状态
       -> auth logged_in: session active
       -> auth login pending: 人工 login.sh
       -> container/health/API 异常: 排障，不扫码
```

容器自动恢复与微信会话恢复是两个独立层次。restart policy 只能恢复进程；微信服务是否
仍信任该会话必须由 auth API 验证。

## 状态分层

`status.sh` 输出五项：

1. `Container`：Docker 容器 running/stopped/unknown；
2. `Container Health`：healthy/starting/unhealthy/none/unknown；
3. `API`：宿主 `/health` reachable/unavailable；
4. `Auth`：`logged_in`、登录等待、`app_not_running` 或未知；
5. `Session`：active/login_required/unavailable。

只有容器 running、Docker health healthy、API reachable 且 auth `logged_in` 时返回 `0`。
需要登录返回 `2`；管理或访问错误返回 `1`；运行态不满足要求返回 `3`。

## QR 登录路径

```text
status confirms login required
  -> login.sh opens WebSocket /api/ws/login?newAccount=true
  -> terminal renders fresh QR
  -> phone scan and confirmation
  -> login_success only accepted after QR render
  -> auth API confirms logged_in
```

已有 session 为 `logged_in` 时 `login.sh` 直接返回，不创建新 QR。QR 登录只恢复认证，
不会轮换或删除持久目录。

## 恢复单元与故障隔离

`data`、`wechat-home` 和原 `auth-token` 是不可拆分的恢复单元。典型边界：

- 容器故障：保留宿主数据，重启/重建容器；
- auth 失效：保留宿主数据，重新 QR 登录；
- 数据损坏或丢失：停止服务，恢复完整一致备份；
- Gateway 调用失败：先确认本服务四层状态和网络，再转交调用方责任域。

禁止通过 `down -v`、删除 HOME、生成新 Token 或切换到空根目录处理一般故障。

## 配置边界

三个主要路径变量：

- `CF_AGENT_WECHAT_ROOT`：代码和 Compose 根；
- `CF_GATEWAY_ROOT`：仅检查的外部 Gateway 根；
- `CF_RUNTIME_ROOT`：本项目持久根。

镜像、bind IP、端口和容器名由 `docker/.env` 管理。首次缺少该文件时 bootstrap 接受
digest-pinned `AGENT_WECHAT_IMAGE` 并原子创建；后续 `.env` 是权威输入，调用 shell 中
相同变量若与文件冲突会失败。
